Why it matters

CUSTOMER 01

아이디어를 문제로 전환

CUSTOMER 02

문서가 아닌 체험

핵심 사용자 흐름을 프로토타입으로 보고, 실제 사용자에게 물어볼 설문을 만듭니다.

SA / AM 03

후속 기회의 구체화

Discovery에서 드러난 요구사항·데이터·통합·검증 과제를 Inception과 Construction 논의로 연결합니다.

Method first, tool second

고객에게 남는 것은 방법론입니다

Pathfinder는 제품이 아니라 실행 환경입니다. 공개된 방법론을 비개발자가 브라우저에서 수행할 수 있도록 질문, 문서, 프로토타입 접점을 제공합니다.

Workshop → build

워크숍은 끝이 아니라 실제 빌드의 출발점입니다

AI-PLC Discovery에서 확인한 문제와 제품 가설을 후속 AI-Driven Development Life Cycle (AI-DLC) engagement의 입력으로 정제하면, 요구사항과 설계부터 실제 코드·테스트·배포까지 하나의 빌드 여정으로 이어갈 수 있습니다.

01 · AI-PLC DISCOVERY

무엇을, 왜 만들지 검증

  • Discovery Document
  • 검증할 제품 범위와 우선순위
  • PROTOTYPE-*.md와 체험 결과
  • 사용자 피드백과 미검증 가정
02 · VALIDATED HANDOFF

산출물을 Build Intent로 정제

  • 실험용 기능과 MVP 범위 구분
  • 가정·제약·데이터 준비도 확인
  • 성공 기준과 추적성 연결
  • 개발팀 참여 범위와 품질 기준 합의
03 · AI-DLC ACTUAL BUILD

실제 소프트웨어로 구현

  • 요구사항·아키텍처·작업 단위 구체화
  • 애플리케이션 코드와 테스트 생성
  • Build·quality gate·CI/CD 구성
  • 필요한 범위의 배포·관측·개선

CUSTOMER-FACING BRIDGE MESSAGE

“오늘 만든 데모를 그대로 production에 올리는 것은 아닙니다. 대신 고객에게 확인한 문제, 선택한 범위, 프로토타입과 반응 데이터를 후속 AI-DLC의 출발점으로 삼아 실제 요구사항과 설계, 코드와 테스트를 갖춘 소프트웨어 빌드로 이어갈 수 있습니다.”

Follow-on engagement

SA·AM이 제안할 다음 여정

후속 구간고객과 함께 할 일다음 결과
1. Handoff Review워크숍 산출물, 검증 결과, 미해결 가정과 기술 제약을 리뷰하고 실제 개발 범위를 합의Build Intent와 AI-DLC 적용 범위
2. AI-DLC Actual Build요구사항과 설계를 구체화하고, review 가능한 단위로 코드 생성·build and test·CI/CD·필요한 배포를 수행테스트된 애플리케이션과 운영 가능한 전달 경로
세일즈 포인트: 워크숍은 단발성 아이데이션이 아니라 실제 개발을 시작하기 전에 모호함을 줄이는 Build Qualification입니다. 단, Pathfinder에서 AI-DLC로 one-click 전환되는 것은 아니며, 개발팀이 참여하는 별도 후속 engagement로 scope와 품질 기준을 합의해야 합니다.

Account fit

누구에게 제안해야 하는가

가장 좋은 고객은 “문제와 의지는 있지만 해법은 아직 열려 있는” 고객입니다.

적합도가 높은 신호

  • 생성형 AI를 검토하지만 첫 Use case를 못 고르고 있다
  • 아이디어가 여러 개라 우선순위 합의가 필요하다
  • 개발 투자 전에 사용자 흐름을 먼저 확인하고 싶다
  • PM·현업·IT가 같은 그림을 보고 대화할 필요가 있다
  • 비즈니스 오너가 반일 동안 직접 의사결정할 수 있다
  • 실데이터 대신 합성·예시 데이터로 탐색할 수 있다

이번 워크숍과 맞지 않는 신호

  • 요구사항이 이미 확정되어 개발 견적만 필요하다
  • 반일 안에 운영 가능한 PoC나 production 배포를 원한다
  • 성능·보안·실데이터 정확성 검증이 주목적이다
  • 기존 시스템 연동을 현장에서 완성해야 한다
  • 비즈니스 의사결정자 없이 IT 실무자만 참석한다
  • 고객 개인정보나 기밀 원본 데이터를 반드시 써야 한다

Objection handling

자주 받는 질문과 답변

“리포를 받아서 직접 돌리면 되지 않나요?”

가능합니다. 다만 원래 실행 방식은 Claude Code나 Kiro 같은 개발자 도구, 터미널, Git workspace, 마크다운 질문 파일 편집이 필요합니다. 참가자는 PM·기획자이고 그들에게 필요한 것은 방법론이지 개발 환경이 아닙니다. Pathfinder는 그 실행 장벽을 브라우저 UI로 바꿉니다.

“AI-PLC가 무엇인가요?”

AWS가 공개한 AI 기반 제품 라이프사이클 방법론입니다. Discovery → Inception → Construction → Operations 네 phase로 구성되며, 이번 워크숍은 첫 번째인 Discovery를 다룹니다.

“Pathfinder는 AWS 제품인가요?”

아닙니다. 공개된 방법론을 워크숍에서 브라우저로 실행하기 위한 도구입니다. 고객에게 제안하는 핵심은 방법론과 Discovery 경험이며, Pathfinder는 반나절 안에 수행하도록 돕는 수단입니다.

“우리도 ChatGPT나 Copilot을 쓰고 있습니다. 무엇이 다른가요?”

도구 사용 교육이 아니라 제품 의사결정 절차입니다. 고객 문제, 우선순위, 승인 게이트, 프로토타입, 검증 결과가 하나의 흐름과 산출물로 남습니다.

“이 결과가 PoC인가요?”

아닙니다. 사용자 흐름과 제품 방향을 확인하는 Discovery 프로토타입입니다. 성능, 보안, 실데이터 정확성, 운영 준비도는 후속 Inception과 Construction에서 다룹니다.

“고객 데이터를 넣어야 하나요?”

권장하지 않습니다. 워크숍에서는 합성·예시 데이터를 사용하며, 개인정보와 고객 기밀 원본은 입력하지 않는 것을 원칙으로 합니다.
