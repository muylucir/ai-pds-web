반일 핸즈온(Path A)의 당일 진행 대본입니다. 단계마다 화면에서 무엇이 일어나는지 · 진행자가 개입할 지점 · 흔한 막힘을 정리했습니다. 참가자용 소개자료는 intro.html입니다.

🕘 반일 · 약 4시간 👥 PM · 기획자 🧭 Path A 🖥️ 1인 1환경 (참가자별 EC2)

한 장 요약 — 오늘 지켜야 할 세 가지 먼저 읽기

나머지를 다 잊어도 이 셋만 지키면 워크샵은 굴러갑니다.

Rule 01

1인 1환경 — 서로 간섭하지 않는다

참가자는 각자 자기 EC2를 받습니다. 백엔드도 각자의 것이라 빌드 상한·산출물·계정이 전부 분리됩니다. 남이 빌드해도 내 순서가 밀리지 않습니다. 대신 각자의 URL을 정확히 전달하는 것이 진행자의 일이 됩니다 — 남의 URL로 들어가면 남의 프로젝트가 보입니다.

Rule 02

승인은 참가자가 누른다

시간에 쫓겨 진행자가 대신 승인하면 워크샵의 핵심 경험이 사라집니다. 게이트는 "AI가 만든 것을 사람이 판단하는" 순간이고, 그걸 체험하러 온 자리입니다. 시간을 줄이려면 논의 시간을 줄이되 승인은 본인이.

Rule 03

느린 것은 대체로 정상

에이전트가 생각하는 중이거나 빌드가 도는 중입니다. 참가자가 "멈춘 것 같다"고 할 때 새로고침·재시작을 권하지 마세요 — 진행 중인 턴을 잃습니다. 먼저 화면의 진행 표시를 함께 확인합니다.

🚨 당일 아침에 반드시 확인할 것

① 참가자 환경 전부가 열리고 로그인이 되는가 — 1인 1환경이므로 한 대씩 확인해야 합니다. 한 대만 죽어 있어도 그 참가자는 오늘 아무것도 못 합니다. ② 각 환경에서 프로젝트를 만들어 첫 메시지에 에이전트가 응답하는가(= Bedrock 연결 확인) ③ URL–참가자 배정표가 정확한가. 하나라도 실패하면 워크샵을 시작하지 말고 먼저 해결하세요 — 실습 중에 발견하면 복구할 시간이 없습니다.

🖥️ 1인 1환경이 바꾸는 것 — 진행자가 알아야 할 차이

좋아지는 것: 빌드 대기가 없어 순번 운영이 불필요하고, 참가자가 서로의 진행을 망칠 수 없습니다. 각자 자기 속도로 갑니다.

대신 생기는 일: 문제가 1인분씩 따로 발생합니다. 공용 환경이면 한 번 고치면 전원이 풀리지만, 이제는 참가자마다 다른 지점에서 막힙니다. 진행자 혼자 8명을 보는 것은 어렵습니다 — 참가자 6명이 넘으면 보조 진행자를 두세요. 그리고 진행 속도가 벌어지므로 단계마다 싱크 포인트를 잡아 빠른 사람을 기다리게 하는 운영이 필요합니다.

사전 준비 전날까지

배포·설정 상세 절차는 리포의 README.md와 infra/README.md에 있습니다. 여기서는 워크샵 운영에 직접 영향을 주는 것만 다룹니다.

환경 준비 — 1인 1환경

참가자마다 워크샵용 EC2를 하나씩 받습니다. 각 환경이 백엔드·프론트·인증·산출물을 모두 자체적으로 갖기 때문에, 준비 작업이 참가자 수만큼 반복됩니다. 여기가 이 워크샵 준비의 대부분입니다.

  • 참가자 수만큼 환경 배포 — 전날까지배포 1건에 15~20분이 걸리고 대부분이 대기 시간입니다(첫 부팅 빌드 + CDN 배포). 여러 대는 병렬로 돌리세요. 배포 직후 몇 분간 502는 정상입니다. 당일 아침에 시작하면 절대 못 끝냅니다.
  • 환경마다 접속·로그인·첫 턴 응답 확인배포 성공 ≠ 동작. 한 대씩 열어 로그인하고, 프로젝트를 만들어 메시지를 한 번 보내 에이전트가 응답하는지 보세요. 이게 Bedrock 연결까지 한 번에 검증하는 가장 빠른 방법입니다.
  • Bedrock 모델 액세스 활성화배포 리전 콘솔에서 사용할 Claude 모델을 켜 둡니다. 계정 단위 설정이라 같은 계정에 여러 대를 배포하면 한 번만 하면 됩니다. 빠뜨리면 배포는 성공하고 첫 대화 턴에서 실패합니다.
  • URL–참가자 배정표 만들기1인 1환경의 핵심 준비물. 누가 어느 URL인지 표로 만들어 개별 전달하세요(전체 채팅에 나열하면 반드시 남의 것에 들어갑니다). 이름과 URL을 나란히 둔 쪽지·DM이 가장 확실합니다.
  • 로그인 계정 확인각 환경에 동일한 시드 계정이 들어 있습니다(관리자 1 · PM 1, 비밀번호 공통). 환경이 분리되어 있으므로 같은 계정을 써도 서로 간섭하지 않습니다 — 참가자별로 계정을 따로 만들 필요가 없어 준비가 간단해집니다. 데모용 비밀번호이므로 워크샵 후 환경을 반드시 내립니다.
  • 예비 환경 1대당일 한 대가 죽으면 그 참가자는 아무것도 못 합니다. 여분 1대를 미리 띄워 두세요 — 현장에서 새로 배포하면 20분이 날아갑니다.

진행자 리허설 — 생략하지 마세요

  • 당일 시나리오로 전 과정 1회 완주페인 포인트 입력부터 프리뷰 열기·설문 집계까지. 목적은 두 가지: ① 실제 소요 시간 측정(이 자료의 분 배분을 여기서 확정) ② 오늘 쓸 도메인에서 에이전트가 어떤 질문을 하는지 미리 보기.
  • 프로토타입 빌드 소요 시간 실측가장 편차가 큰 구간입니다. 측정값이 45분을 넘으면 시나리오 범위를 줄이거나(기능 2개로) 빌드를 진행자 시연으로 전환할 준비를 하세요.
  • 리허설 산출물은 지우거나 별도 프로젝트로참가자가 만들 프로젝트와 섞이지 않게 합니다.

강의실 준비

  • 참가자 배포물본인 전용 접속 URL · 로그인 계정 · intro.html · 실습 시나리오 텍스트. 시나리오와 URL은 반드시 복사 가능한 형태로 주세요 — 받아 적게 하면 10분이 날아가고 오타로 헤맵니다.
  • 네트워크 확인참가자 전원이 각자 다른 호스트로 접속하고 SSE 스트리밍을 유지합니다. 게스트 와이파이의 프록시가 스트리밍을 끊지 않는지 미리 확인하세요 — 여기서 막히면 화면이 멈춘 것처럼 보입니다.
  • 화면 공유 준비진행자 화면으로 첫 단계를 시연한 뒤 참가자가 따라오는 방식이 가장 매끄럽습니다. 진행자 환경도 참가자와 동일한 구성이어야 시연이 어긋나지 않습니다.
  • 보조 진행자 확보참가자 6명 초과면 필수. 1인 1환경에서는 문제가 개별적으로 발생해 진행자 한 명이 순회 대응하기 어렵습니다.
⚠️ 워크샵이 끝나면 환경을 전부 내리세요 — 대수만큼 비용이 곱해집니다

환경 하나당 서버 상시 가동 + 스토리지 + 대화마다 모델 호출 비용이 발생하고, 1인 1환경이므로 참가자 수만큼 곱해집니다. 방치가 가장 비싼 실수입니다. 순서: ① 참가자 전원이 산출물 zip을 받았는지 확인 → ② 환경 삭제. 삭제하면 계정과 산출물이 함께 사라집니다 — 되돌릴 수 없습니다. 내린 환경을 체크리스트로 지워가며 한 대도 남기지 마세요. 상세 절차는 리포 README의 삭제 절 참고.

📌 진행 속도 관리 — 1인 1환경에서 실제로 필요한 운영

빌드 대기가 없어진 대신 참가자별 속도 차이가 그대로 벌어집니다. 빠른 사람은 먼저 끝내고 기다리고, 막힌 사람은 혼자 뒤처집니다. 대응: 단계마다 싱크 포인트를 두고("PR/FAQ 승인까지 하신 분?") 전체 진행률을 확인한 뒤 다음으로 넘어가세요. 먼저 끝낸 참가자에게는 검증 설문 문항 미리 만들기나 PR/FAQ 다듬기를 주면 대기가 학습이 됩니다.

# 비즈니스 컨텍스트 (붙여넣기)
우리는 중소 규모 온라인 패션 쇼핑몰을 운영한다. 월 주문은 약 3만 건이고
고객센터는 상담원 4명이 채팅과 이메일로 응대한다.

문의의 대부분이 반품·교환·배송 조회에 몰려 있고, 상담원은 같은 질문에
반복해서 답한다. 문의가 들어오면 상담원이 주문 시스템을 따로 열어 주문번호를
찾고, 배송사 사이트에서 배송 상태를 확인한 뒤 답변한다.

문의는 저녁 8시~자정에 가장 많이 들어오는데 그 시간에는 상담원이 없어
다음 날 오전에 답변이 나간다. 고객은 그 사이 여러 번 문의를 다시 남기거나
그냥 이탈한다. 상담원 이직률도 높다.

목표는 반복 문의를 자동으로 처리해 상담원이 진짜 판단이 필요한 건에만
집중하게 하는 것이다.

페인 포인트 단계에서 유도할 답변

에이전트가 심각도·빈도·현재 대응 방식을 물어옵니다. 참가자가 막히면 아래를 힌트로 주세요 — 답을 대신 주지 말고 방향만.

# 진행자 힌트 카드 (참가자가 막힐 때만)
가장 아픈 것   야간 문의가 다음 날로 밀린다 → 이탈로 이어진다
가장 잦은 것   "내 주문 어디까지 왔나" · "반품 어떻게 하나"
현재 대응     상담원이 주문 시스템 + 배송사 사이트를 손으로 왕복
참는 이유     챗봇을 넣었다가 엉뚱한 답을 해서 걷어낸 경험이 있다
성공의 모습   야간 문의의 절반이 사람 없이 해결되고 고객이 만족한다
🎭 다른 도메인을 쓰고 싶다면

고객사 맞춤으로 바꾸는 것을 권장합니다. 조건은 셋: ① 참가자가 페인 포인트를 경험으로 말할 수 있다 ② 프로토타입이 화면 2~3개로 표현된다 ③ "이게 좋아졌는지"를 사용자에게 물을 수 있다. 사내 시스템처럼 참가자만 아는 도메인도 좋지만, 범위가 커지지 않게 진행자가 미리 좁혀 두세요.

⚠️ 범위 확장이 시간을 잡아먹는 1번 원인

참가자는 자연히 기능을 늘립니다("추천도 넣고, 재고 연동도…"). Envision 단계에서 "오늘 프로토타입으로 확인할 가설 하나"로 좁히도록 계속 당겨 주세요. 명세 단계에서 기능이 5개를 넘으면 빌드가 45분을 넘깁니다.

단계별 진행 대본 현장용

단계마다 화면에서 무엇이 일어나는가 / 진행자가 할 일 / 흔한 막힘. 🗣 표시는 그대로 말해도 되는 문장입니다.

1 접속 · 프로젝트 생성 · Path A 선택 15분
화면에서 일어나는 일
  • 로그인 후 프로젝트 목록. 프로젝트 ID(영문·숫자)와 이름(선택)을 넣어 생성.
  • 워크스페이스 탭에 들어가면 시작 카드가 뜹니다 — Path A / Path B 두 버튼.
  • Path A를 누르면 그 문장이 첫 메시지로 전송되고 에이전트가 Discovery를 시작합니다.
진행자가 할 일
  • 진행자 화면으로 한 번 시연한 뒤 참가자가 따라오게 합니다.
  • 프로젝트 ID는 본인 이름/이니셜로 정하게 하세요(jihoon, minji…). 환경이 각자 분리되어 있어 충돌은 없지만, 나중에 산출물을 찾고 화면 공유로 서로 볼 때 편합니다.
  • 주소창의 호스트가 본인 것인지 한 번 확인시키세요. 남의 URL로 들어가도 로그인이 되므로(시드 계정이 동일) 본인은 알아채지 못합니다 — 이 확인이 오늘 가장 흔한 사고를 막습니다.
  • 전원이 에이전트의 첫 응답을 받은 것까지 확인하고 다음으로 넘어갑니다. 여기서 낙오하면 이후 전부 어긋납니다.
흔한 막힘
  • 이미 존재하는 프로젝트 ID — 환경이 분리되어 있으므로 남과 겹친 게 아니라 본인이 이미 만든 것입니다(리허설·재시도 흔적). 기존 프로젝트로 들어가거나 다른 ID를 쓰게 하세요.
  • 첫 응답이 오지 않는다 — Bedrock 액세스 문제일 수 있습니다. 트러블슈팅 §7 첫 항목.
  • 탭이 회색으로 눌리지 않음 — 프로젝트를 아직 선택하지 않은 상태입니다. 정상 동작.

"지금부터는 여러분이 PM입니다. AI가 질문을 하면 답하고, 결과가 마음에 안 들면 고쳐 달라고 하세요. 그게 오늘의 일입니다."

2 Envision — 페인 포인트 · PR/FAQ 50분 · 최장 구간
화면에서 일어나는 일
  • 먼저 비즈니스 컨텍스트 입력 방식을 객관식으로 물어옵니다(직접 설명 / URL 분석 / 둘 다 / 질문받기). 오늘은 직접 설명.
  • 참가자가 컨텍스트를 붙여넣으면 에이전트가 부족한 부분만 추가 질문합니다.
  • 페인 포인트를 정리해 분석 문서를 만들고, 이어서 PR/FAQ를 작성합니다.
  • 문서는 워크스페이스 오른쪽 패널에 바로 나타납니다. 문서 리뷰 탭으로 이동할 필요 없습니다.
  • PR/FAQ가 완성되면 승인 요청이 옵니다.
진행자가 할 일
  • 범위를 계속 좁히세요. 참가자가 기능을 늘리려 할 때 "오늘 확인할 가설 하나"로 되돌립니다.
  • PR/FAQ가 나오면 반드시 읽게 하세요. 스크롤만 하고 승인하는 것이 가장 흔한 실수입니다.
  • 한 팀에게 수정 요청을 일부러 시켜 보게 하고 그 결과를 전체에 공유하면, 게이트의 의미가 단번에 전달됩니다.
  • 30분 지점에서 진행률 점검. PR/FAQ 초안이 안 나온 팀이 있으면 컨텍스트를 더 짧게 잡아 주세요.
흔한 막힘
  • 질문이 계속 이어진다 — 컨텍스트가 모호할수록 질문이 길어집니다. 구체적으로 답하게 하거나 시나리오 문구를 그대로 쓰게 하세요.
  • PR/FAQ가 어색하다는 반응 — 정상입니다. 소개자료 §5의 Working Backwards 설명을 다시 짚어 주세요.
  • URL 분석을 고른 팀 — 외부 URL은 시간이 걸리고 결과 편차가 큽니다. 오늘은 직접 설명으로 통일하는 것을 권장합니다.

"이 보도자료를 고객이 읽었다고 상상해 보세요. '그래서 내가 뭐가 편해지는데?'에 답이 있습니까? 없으면 아직 문제를 덜 이해한 겁니다."

3 솔루션 분석 · 프로토타입 명세 25분
화면에서 일어나는 일
  • 에이전트가 PR/FAQ를 분석해 솔루션이 하나인지 여러 개인지 판별하고 성격(에이전트형/애플리케이션형)을 분류합니다.
  • 여러 개면 무엇을 프로토타입할지 고르게 합니다.
  • 선택된 솔루션으로 프로토타입 명세를 작성합니다 — 기능·화면·데이터·검증 가설.
  • 명세가 저장되면 프로토타입 탭에 카드가 생깁니다. 에이전트는 여기서 "프로토타입 탭에서 빌드하라"고 안내하며 턴을 마칩니다.
진행자가 할 일
  • 명세의 기능 개수를 확인하세요. 5개를 넘으면 빌드가 길어집니다 — 2~3개로 줄이게 합니다.
  • 검증 가설을 특히 보게 하세요. 나중에 설문 문항이 여기서 나옵니다. 가설이 흐리면 설문도 흐려집니다.
  • 명세 승인 후 프로토타입 탭에 카드가 떴는지 전원 확인. 안 뜨면 즉시 트러블슈팅 §7의 "카드가 안 뜸" 항목.
흔한 막힘
  • 카드가 안 뜬다 — 명세가 규정된 경로/파일명으로 저장되지 않았을 때 발생합니다. §7 참조. 가장 알아둘 가치가 있는 현상입니다.
  • "에이전트가 빌드까지 해줄 줄 알았다" — Pathfinder에서 Discovery는 명세까지입니다. 빌드는 프로토타입 탭 전담이라고 설명하세요(호스팅·프리뷰를 그 탭만 다룰 수 있기 때문).
  • 명세에 포트 번호가 적혀 있다 — 무시하세요. 포트는 빌드 시점에 자동 배정됩니다.
4 프로토타입 빌드 · 호스팅 · 프리뷰 45분 · 병목
화면에서 일어나는 일
  • 카드의 빌드 시작 → 빌드 드로어가 열리고 빌드 에이전트가 명세를 읽어 작업을 시작합니다.
  • 진행 중 질문이 오면 워크스페이스와 같은 질문 폼으로 답합니다. 중단도 가능합니다.
  • 완료되면 카드가 빌드 완료로. 호스팅 시작을 누르면 실행 중이 되고 포트가 표시됩니다.
  • 프리뷰 열기로 새 탭에서 실제 앱을 만져봅니다. 다운로드로 결과물 zip을 받을 수 있습니다.
진행자가 할 일
  • 전원 동시에 시작해도 됩니다. 각자 자기 환경이라 서로 순서를 기다리지 않습니다 — 참가자에게 "동시에 눌러도 된다"고 명확히 알려주세요.
  • 완료 시점이 크게 벌어집니다. 명세 범위에 따라 편차가 크니, 먼저 끝낸 사람에게 할 일을 주세요 — 검증 설문 문항 미리 생성(빌드 전에도 됩니다) 또는 PR/FAQ 다듬기.
  • 빌드가 도는 동안 진행 로그를 화면 공유하면 대기 시간이 학습 시간이 됩니다. "지금 무슨 파일을 만드는지" 함께 보기.
  • 휴식 시간에 빌드 세션을 방치하지 않게 — 30분 유휴면 자동 종료됩니다.
  • 프리뷰가 열리면 반드시 만져보게 하세요. 이게 오늘의 하이라이트입니다.
흔한 막힘
  • 빌드 실패 — 카드에서 로그를 확인하고 다시 빌드. 명세 범위가 크면 반복 실패하니 기능을 줄여 재시도.
  • 빌드 시작이 거부됨 — 자기 환경의 동시 빌드 상한(기본 10건)에 닿은 경우입니다. 1인 1환경에서 참가자가 여기에 닿는 일은 사실상 없으니, 이 증상이 나오면 이전 빌드가 정리되지 않았는지 먼저 확인하세요(§7 참조). 대기열이 아니라 그 자리에서 거절되므로 잠시 후 다시 누르면 됩니다.
  • 프리뷰가 404/빈 화면 — §7 참조. 호스팅이 아직 올라오는 중일 수 있으니 잠시 후 다시.
  • 세션이 끊겼다 — 다시 열면 이전 대화를 이어받습니다. 처음부터 다시 설명하지 않게 안내하세요. 단 초기화를 눌렀다면 만들어진 코드가 지워졌으므로 에이전트가 명세를 다시 읽어 처음부터 만들자고 제안합니다(정상 동작).

"방금 여러분이 만진 건 목업이 아니라 실제로 도는 앱입니다. 오늘 아침에 있던 건 고객의 불편 하나뿐이었습니다."

5 검증 설문 25분 · 압축 가능
화면에서 일어나는 일
  • 카드의 설문 버튼 → 질문 생성을 누르면 명세의 검증 가설·기능 목록에서 문항이 만들어집니다.
  • 링크 복사로 로그인이 필요 없는 응답 링크를 얻습니다.
  • 응답이 들어오면 집계 대시보드에 반영됩니다(5점 척도 · 객관식 · 서술형).
  • 결과 취합으로 집계를 문서로 저장, 설문 마감 후 CSV 내보내기.
진행자가 할 일
  • 교차 응답을 조직하세요 — 각자의 설문 링크를 전체 채팅에 모으고 서로의 프로토타입에 응답하게 합니다. 1인 1환경이라 결과물이 사람마다 달라 비교가 재미있고, 남의 결과를 보는 부수 효과가 큽니다.
  • 설문 링크는 인증이 없어 환경 밖에서도 열립니다 — 다른 참가자가 자기 브라우저에서 바로 응답할 수 있습니다. 이게 교차 응답이 가능한 이유입니다.
  • 응답자에게 한 문장 안내하세요 — 문항은 "완성도"가 아니라 "이 방향이 맞는가"를 묻습니다. 데이터가 임시고 일부 화면은 껍데기이므로 속도·안정성·데이터 정확도는 문항에 없습니다. 그리고 안 써 본 기능은 "사용하지 않았다"를 고르게 하세요 — 짧은 체험에서 모든 기능에 닿지 못하는 것이 정상이고, 추측으로 평가하면 집계가 잡음이 됩니다. (설문 화면 상단에 같은 안내가 있습니다.)
  • 응답 후 새로고침해서 집계가 올라가는 것을 함께 확인합니다.
  • 시간이 부족하면 진행자 화면으로 문항 생성 → 링크 → 집계까지 5분 시연으로 압축하세요.
  • 설문은 빌드 상태와 무관하게 열 수 있다고 알려주세요 — 빌드가 도는 동안이나 먼저 끝낸 참가자가 미리 만들어 둘 수 있습니다.
흔한 막힘
  • 문항이 엉뚱하다 — 명세의 검증 가설이 흐렸다는 신호입니다. 이 인과관계를 짚어주면 좋은 학습 포인트가 됩니다.
  • 링크가 안 열린다 — 참가자에게 전달된 링크가 잘렸는지 확인. 채팅으로 붙여넣게 하세요.
  • 집계가 안 보인다 — 새로고침이 필요합니다. 응답과 대시보드가 실시간 연동은 아닙니다.
6 문서 리뷰 · 승인 · 핸드오프 20분
화면에서 일어나는 일
  • 문서 리뷰 탭 — 왼쪽에 문서 목록, 오른쪽에 본문. Discovery 문서가 기본 선택됩니다.
  • 미승인 상태면 승인 게이트가 상단에 뜹니다. 승인하면 완료 표시로 바뀝니다.
  • 수정 요청을 하면 승인이 무효화되고 게이트가 다시 나타납니다.
  • 전체 다운로드(.zip)로 산출물 전체를, .md 다운로드로 개별 문서를 받습니다.
진행자가 할 일
  • 승인은 참가자가 누르게 하세요. 마지막까지 이 원칙을 지킵니다.
  • "수정하면 승인이 다시 필요해진다"를 실제로 보여주세요 — 문서가 살아있는 계약이라는 감각이 생깁니다.
  • zip을 받아 열어보게 하세요. 개발팀에 넘길 것이 무엇인지 눈으로 확인하는 것이 핸드오프 설명보다 강력합니다.
  • 프로토타입 결과물 zip도 함께 받게 하세요 — 환경을 내리면 사라집니다.
흔한 막힘
  • Discovery 문서가 비어 있다 — 아직 종합 단계까지 가지 않은 것입니다. 워크스페이스에서 문서 종합을 요청하게 하세요.
  • 승인 버튼이 안 보인다 — 이미 승인된 상태이거나 Discovery 문서가 아닌 파일을 보고 있습니다.

게이트 운영 — 워크샵의 핵심

참가자가 오늘 배워야 할 단 하나를 고른다면: AI가 만든 것을 사람이 판단하는 경험입니다. 게이트가 그 순간입니다.

🚫 하지 말아야 할 것

진행자가 대신 승인하기. 시간에 쫓기면 가장 하고 싶어지는 일이고, 워크샵의 가치를 가장 크게 훼손하는 일입니다. 승인을 대신 누르면 참가자는 "AI가 알아서 해주는 도구"를 보고 돌아갑니다 — 정확히 반대의 교훈입니다. 시간을 줄여야 하면 논의 시간을 줄이되 클릭은 본인이 하게 하세요.

게이트에서 진행자가 던질 질문

게이트이때 물어볼 것
페인 포인트 분석 "이게 우리 고객의 문제입니까, 아니면 일반적으로 그럴 것 같은 문제입니까?" — 가장 흔한 오류가 일반론으로 흐르는 것입니다.
PR/FAQ 핵심 "고객이 이걸 읽고 무엇이 편해지는지 알 수 있습니까?" / "여기 적힌 고객이 실제 우리 고객입니까?"
솔루션 선택 "이 솔루션이 아까 그 페인 포인트를 푸는 게 맞습니까? 다른 문제를 풀고 있지 않습니까?"
프로토타입 명세 범위 관리 "이걸 만들면 어떤 가설이 확인됩니까?" / "기능 중 빼도 되는 것은 무엇입니까?"
Discovery 문서 "이 문서만 받은 개발팀이 무엇을 만들지 알 수 있습니까? 빠진 게 있습니까?"
✅ 수정 요청을 최소 한 번은 시키세요

전원이 계속 승인만 하고 끝나면 게이트를 경험한 게 아닙니다. PR/FAQ 단계에서 한 팀에게 일부러 수정 요청을 시키고, AI가 어떻게 고쳐 오는지 전체에 공유하세요. "고칠 수 있다"를 본 참가자는 이후 게이트를 진지하게 봅니다.

트러블슈팅 · FAQ 현장 대응

증상 → 원인 → 대처. 위쪽이 더 자주 발생하는 순서입니다.

증상원인 / 대처
첫 대화 턴에서 권한 오류
치명적		 배포 리전에 Bedrock 모델 액세스가 활성화되지 않았습니다. 콘솔에서 해당 Claude 모델을 켜야 합니다. 당일 아침 점검에서 반드시 걸러낼 항목 — 실습 중 발견하면 대응 시간이 없습니다.
남의 화면이 보인다 / 내 산출물이 없다
1인 1환경 특유		 다른 참가자의 URL로 접속했습니다. 1인 1환경이라 URL이 곧 사람이고, 시드 계정이 모든 환경에서 동일해 로그인은 정상적으로 됩니다 — 그래서 본인은 알아채기 어렵습니다. 배정표로 URL을 확인시키세요. 가장 흔하고 가장 헷갈리는 사고이므로, 실습 시작 전에 "주소창의 호스트가 본인 것인지" 한 번 확인시키고 넘어가세요.
빌드 시작이 거부됨 자기 환경의 동시 빌드 상한(기본 10건)에 닿았습니다 — 다른 참가자와는 무관합니다. 1인 1환경에서 참가자가 10건을 동시에 돌릴 일은 없으므로, 이 증상이 나오면 이전 빌드 세션이 정리되지 않은 것을 의심하세요(카드에서 세션을 닫거나 초기화). 문구는 카드 목록 위의 "동시 빌드 상한(N건)에 도달했습니다"와 시작 시점의 "다른 팀이 프로토타입을 빌드하고 있습니다 — 잠시 후 다시 시도해 주세요" 두 가지이며, 후자는 공용 환경을 전제한 문구라 1인 1환경에서는 오해를 부릅니다. 대기열에 들어가는 것이 아니라 그 자리에서 거절되므로 잠시 후 다시 누르면 됩니다.
프로토타입 카드가 안 뜬다 명세가 규정된 디렉터리·파일명 규약을 벗어나 저장됐습니다(카드 목록은 그 경로만 인식). 대처: 워크스페이스에서 "프로토타입 명세를 규정 경로에 다시 저장해 달라"고 요청하게 하세요. 문서 리뷰 탭에서 파일 위치를 함께 확인하면 원인이 보입니다.
화면이 멈춘 것 같다 대부분 에이전트가 처리 중입니다(정상). 새로고침·재시작을 권하지 마세요 — 진행 중인 턴을 잃습니다. 진행 표시를 함께 확인하고, 수 분 이상 변화가 없으면 그때 페이지를 새로 열게 합니다(대화 기록은 복원됩니다).
다시 들어왔더니 채팅이 이상하다 과거에는 도구만 호출한 턴이 빈 말풍선으로 줄줄이 복원되는 현상이 있었습니다 — 지금은 한 턴이 말풍선 하나로 모이고, 도구 실행은 그 아래 "추론 과정"에 접혀 들어갑니다. 텍스트 없이 "추론 과정"만 있는 항목은 중단된 턴(자리를 비웠거나 연결이 끊긴 경우)이며 정상입니다. 그래도 비어 보이면 그 자리에서 다음 턴을 진행하게 하세요 — 진행에는 문제가 없습니다.
빌드 세션이 저절로 닫혔다 30분 유휴 자동 종료입니다. 다시 열면 이전 대화를 이어받으므로 처음부터 다시 설명할 필요 없습니다. 휴식 전에 빌드를 방치하지 않도록 미리 안내하세요.
참가자가 "초기화"를 눌러버렸다
되돌릴 수 없음		 카드의 빨간 초기화는 명세만 남기고 만들어진 코드·빌드 대화·검증 설문과 이미 받은 응답까지 지웁니다. 카드는 "스펙만 있음"으로 돌아가므로 다시 빌드하면 복구됩니다 — 다만 빌드 시간을 다시 써야 하고, 설문 응답은 되돌릴 수 없습니다. 교차 응답을 이미 받은 뒤라면 CSV를 먼저 받았는지 확인하세요. 실습 시작 전에 "이 버튼은 처음부터 다시 만들 때만"이라고 한 번 짚어 두면 사고가 줄어듭니다.
빌드 실패 카드의 로그로 원인을 확인하고 다시 빌드. 명세 범위가 크면 반복 실패합니다 — 기능을 2~3개로 줄여 재시도하는 것이 가장 확실한 대처입니다.
프리뷰가 404 / 빈 화면 호스팅이 아직 올라오는 중일 수 있습니다 — 잠시 후 다시 시도. 계속되면 호스팅 중지 → 시작으로 재기동하고, 로그를 확인합니다.
접속 URL이 502를 반환 배포 직후라면 첫 빌드 진행 중이라 정상입니다(수 분~10분). 전날 배포를 끝내 두면 이 상황을 만나지 않습니다. 워크샵 중에 502가 새로 나면 백엔드 상태를 확인해야 합니다.
설문 링크가 안 열린다 링크가 잘려 전달된 경우가 대부분입니다. 링크 복사 버튼으로 다시 복사해 공유하게 하세요. 설문을 마감했다면 응답을 받을 수 없습니다.
설문 집계가 안 올라간다 대시보드는 실시간이 아닙니다. 새로고침을 눌러야 반영됩니다.
로그인 후 리다이렉트 오류 인증 설정의 콜백 URL 등록 문제입니다. 재배포로 해소되는 유형이며 당일 대응이 어렵습니다 — 사전 점검에서 반드시 로그인까지 확인하세요.
참가자 계정이 없다 / 비밀번호를 잊었다 관리자 화면에서 초대 또는 비밀번호 재설정. 새 임시 비밀번호가 화면에 1회만 표시되므로 그 자리에서 전달하세요. 메일은 발송되지 않습니다.
"내 산출물이 사라졌다" 다른 프로젝트를 보고 있을 가능성이 큽니다 — 프로젝트 ID를 확인하게 하세요. 산출물은 보관되므로 브라우저를 닫아도 남습니다.
🧰 진행자용 탈출로

Discovery 에이전트가 특정 단계에서 계속 헤맬 때, 참가자에게 "이 단계를 건너뛰고 다음으로 가 달라"고 입력하게 하는 것이 가장 빠른 복구입니다. Discovery는 절차를 강제하지 않고 상황에 맞춰 조정되므로, 워크샵 진행을 위해 한 단계를 접는 판단은 진행자가 해도 됩니다. 단, 게이트 자체를 건너뛰지는 마세요.

회고 · 핸드오프 15분

만든 것보다 경험한 것을 언어화하는 시간입니다. 여기를 자르면 워크샵이 "도구 시연"으로 기억됩니다.

회고 질문 세트

✏️어디서 AI를 고쳤나

"AI 제안을 수정한 순간이 있었나요? 무엇이 틀렸고, 그걸 어떻게 알았습니까?" — 가장 중요한 질문. 사람의 판단이 필요한 지점을 참가자 스스로 정의하게 만듭니다.

⚖️속도와 통제

"AI가 빠르다고 느낀 곳과, 사람이 개입해야 한다고 느낀 곳은 각각 어디였습니까?"

🧪프로토타입이 바꾼 것

"문서로 합의했던 것과 실제 화면을 본 뒤의 생각이 달라진 부분이 있습니까?" — 프로토타입을 Discovery에 넣는 이유가 여기서 나옵니다.

🏢우리 조직에 적용하기

"여러분의 실제 과제 중 어떤 것에 이걸 써보겠습니까? 그때 Path A와 Path B 중 어느 쪽이 맞습니까?"

💬 회고 진행 팁

전체 토론으로 열면 몇 명만 말합니다. 2분 개인 메모 → 옆 사람과 짝 공유 → 한 명씩 한 가지 발표 순서로 가면 전원이 참여합니다. 1인 1환경이라 각자 다른 결과물을 만들었으니 비교할 이야기가 자연히 나옵니다 — 프리뷰를 화면 공유로 돌아가며 보여주는 것도 좋습니다. 나온 답변은 진행자가 받아 적어 사후 자료로 보내면 워크샵의 수명이 길어집니다.

핸드오프 — 참가자가 가져갈 것

  • Discovery 산출물 zip문서 리뷰 탭 → 전체 다운로드(.zip). 페인 포인트 분석 · PR/FAQ · 명세 · Discovery 문서. 환경을 내리기 전에 반드시 받게 하세요.
  • 프로토타입 결과물 zip프로토타입 카드 → 다운로드. 사내에서 다시 띄우거나 이어서 개발할 수 있습니다. 이것도 환경과 함께 사라집니다.
  • 설문 응답 CSV설문 마감 후 CSV 내보내기. 사후 의사결정 회의에서 쓸 근거 데이터입니다.
  • 다음 단계 안내Discovery 문서를 개발팀에 넘기면 Inception(요구사항·설계) → Construction(구현)으로 이어집니다. 같은 화면에서 Path B(유스케이스 우선순위화)도 할 수 있다고 알려주세요 — 실무 재사용의 출발점입니다.

진행자 사후 정리

  • 참가자 산출물 백업 확인전원이 zip을 받았는지 확인한 뒤에 환경 정리로 넘어갑니다.
