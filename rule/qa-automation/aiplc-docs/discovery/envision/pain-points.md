# QA × AI — 고객 페인포인트 정리 (Envision)

## 주 고객 (Primary Customer)
**QA 엔지니어** — 테스트 케이스(TC)를 직접 설계·실행하고 자동화까지 담당하는 실무자.

## 확정된 초점 (from Envision Q&A)
- **문제 영역 (Q2 = A, B)**
  - A) 정책/기획서 분석 기반 TC 자동 설계 (Figma·Confluence·기획서 → 고품질 TC + 문의사항 도출)
  - B) TC Auto/Manual 자동화 가능 여부 분류 (일관된 기준·사전조건 판별)
- **성공 정의 (Q3 = A, B, C)**
  - A) TC 설계/작성 시간 대폭 단축
  - B) TC/분류 품질·일관성 향상 (휴먼에러·재작업 감소)
  - C) 자동화 안정성·유지보수 효율 향상
- **환경 (Q4 = A)**: Claude / Claude Code 기반

## 원천 페인포인트 (첨부 gcc.xlsx에서 도출)

### 클러스터 1 — 정책/기획서 기반 TC 설계 (핵심)
- 기획 및 디자인 정책이 Figma와 Confluence에 여러 개로 흩어져 있어, 일일이 확인하며 TC 작성에 시간이 과다 소요. 정책 작성 위치(히스토리) 추적에도 리소스 낭비.
- PPT/Figma/Confluence 등 정책 데이터를 AI에 학습시켜 TC를 추출했으나 결과물 수준이 낮아 수차례 수정·수기 보완 필요.
- 문서에 명확히 없거나 이해하기 어려운 부분을 AI가 누락/오해석 → QA가 별도로 문의사항 도출 및 TC 수정/추가에 리소스 투입.
- 정책 데이터 학습 후 일부 항목만 TC 설계 가능, 전체 정책을 충분히 반영 못함.

### 클러스터 2 — TC Auto/Manual 분류 (핵심)
- TC를 자동화/수동으로 판단하는 기준이 담당자 경험·주관에 의존 → 사람마다 판단이 달라 일관성 저하, 검토 시간 과다.
- 구현 단계에서 Manual 대상임을 뒤늦게 발견 → 작업 리소스 낭비.
- CMS 사전 설정/특정 데이터 조건 필요 케이스가 Auto로 오분류되는 문제. 애매한 케이스는 임의 Auto 처리 대신 '휴먼체크'로 분류 필요.
- 판별 기준(사전조건 의존, 데이터 준비 필요, UI 변동성 등)을 프롬프트로 명세화하려는 니즈.

### 관련 인접 페인포인트 (범위 밖이나 참고)
- API 명세(스웨거/컨플/docs) 표준 부재 및 AI 분석·검증 지원.
- API 응답 ↔ DB 컬럼 매칭 기반 TC 기대결과 도출.
- 자동화 테스트 로케이터 자가 치유 / 실패 분석 LLM 보강.
- 릴리즈 회귀 TC 세트 자동 생성/선별.
- 자동화 코드 팀 공유, Slack 알림/스레드 요약, 멀티 에이전트 가드레일.

## 요약 문제 진술 (Problem Statement)
QA 엔지니어는 흩어진 정책/기획 문서를 일일이 해석해 TC를 작성하고, 각 TC의 자동화 가능 여부를 경험에 의존해 판단한다. 이 과정은 **느리고(시간), 사람마다 다르며(일관성), 품질 편차가 크고(재작업), 뒤늦은 오분류로 자동화 리소스를 낭비**한다.
